内存执行

内存执行描述的是载荷在进程内存中运行，不是一种单独的加载手法。它可能与白加黑、动态解码、反射加载、进程注入或安全产品致盲组合出现。最终载荷若不以普通 EXE/DLL 文件落盘，会减少某些文件与模块遥测；但这不等于 EDR 无法采集内存行为。

分析银狐相关样本时，建议分别回答三个问题：载荷从哪里来、在哪个进程中执行、哪些采集链路仍然正常。

攻击链中的位置​

一种多阶段链路可以抽象为：

初始程序或文档启动 Loader
  ↓
取得下一阶段载荷：磁盘数据、程序资源或网络响应
  ↓
在内存中解码，得到 shellcode 或 PE/DLL 内容
  ↓
在本进程执行，或先送入另一个进程
  ↓
载荷运行，产生持久化、通信等后续行为

图中的步骤并非每个样本都具备。尤其要区分“最终载荷不落盘”和“攻击链完全没有文件”：初始 EXE、侧载 DLL、加密容器或驱动仍可能出现在磁盘上。MITRE ATT&CK T1620所说的反射代码加载，可以让载荷直接在进程内存中分配并执行，但不保证整个攻击过程没有文件痕迹。

白加黑：让 Loader 先运行​

白加黑 / DLL 侧加载常利用合法程序原本的 DLL 搜索或插件加载关系，让恶意 DLL 在合法进程内启动。这个阶段通常有一个落盘的 DLL，也可能产生正常的模块加载事件。该 DLL 随后再解码并运行内存载荷，才形成另一段内存执行链。不能把“白程序加载黑 DLL”本身称作无文件反射加载；对应的侧加载分类可参见 MITRE ATT&CK T1574.001。

动态解码与反射加载：减少最终模块落盘​

Loader 可以从数据文件、资源或网络响应中取得编码后的内容，在内存中还原出 shellcode 或 PE/DLL。若后续由自带加载逻辑在内存中装载 DLL，而没有按普通文件路径交给系统加载器，这属于反射加载一类。shellcode 直接运行不一定需要 PE 解析；反射 DLL 则可能需要处理 PE 映像结构。

内存页面可能经历“写入时可写、执行时可执行”的权限变化，也可能采用其他映射方式；RW → RX 是有用的观察线索，并非所有样本都必然出现的固定序列。

进程注入：改变执行所在的进程​

如果 Loader 操作的是自己的地址空间，不一定会出现跨进程写内存或远程线程。若它把载荷送入 svchost.exe 等另一个进程，则还涉及进程注入；执行可能由远程线程、APC、现有线程或其他机制触发。进程空洞化则需要另外检查进程映像是否被替换。MITRE ATT&CK T1055将跨进程注入单独归类。进程注入和反射加载可以连续发生，但观察到其中一个动作，不能自动推断另一个已完成。

BYOVD：削弱防护的另一段链路​

部分攻击会滥用带有合法签名但存在漏洞的驱动（BYOVD）干预安全产品。这不是内存执行的必要条件，也不应把每次内存执行都解释成 EDR 已被致盲。Check Point Research 对一批银狐相关攻击的分析记录了利用脆弱驱动终止安全进程，以及将 ValleyRAT 下载器、最终后门以 DLL 转 shellcode 的形式交付并进行内存反射加载的情况。报告中的具体行为应按样本归纳，不能推广为所有银狐或所有 ValleyRAT 样本的固定步骤。安全产品受损的判断见安全产品致盲。

为什么 EDR 可能少看到一些事件​

EDR 是多种传感器、扫描器和分析逻辑的组合。内存执行通常改变的是可观察的事件种类与质量，而不是让进程内存突然不可观察。

采集面可能减少的信号仍可寻找的证据
文件与静态扫描最终恶意 DLL 没有作为普通文件创建，缺少该 DLL 的磁盘哈希初始程序、容器文件、侧载 DLL、下载和文件读取
正常模块加载手工映射的最终映像可能没有相应的正常 ImageLoad / 模块记录宿主与先前 DLL 的加载事件、内存映像与模块记录差异
用户态 API Hook若样本专门绕过某个 Hook，依赖该 Hook 的调用记录可能缺失内核或系统侧事件、内存状态、线程与后续行为
内存扫描短暂存在的解码内容可能错过某次抽样扫描权限变化、执行地址、按事件触发的扫描和事后内存检查
合法进程外观进程名和主 EXE 签名可能看起来正常载荷所在内存区域、异常模块、调用栈、网络与持久化行为

“绕过用户态 Hook”需要单独证据，不能因为没有 API 日志就断定样本使用了直接系统调用或解除 Hook。相同的缺口也可能来自传感器配置、过滤、版本差异或事件丢失。微软对反射 DLL 加载检测的研究展示了通过异常内存、线程和行为上下文发现这类载荷的思路，因此“内存执行＝EDR 看不到”并不成立。

术语上，Windows 的 AMSI主要提供内容扫描集成接口，不能代指所有文件或内存监控；AMFI 则不是 Windows 的文件监控组件。

EDR 可以如何观察​

文件、模块与驱动​

有落盘启动器或侧载 DLL 时，文件创建和模块加载仍有价值。以 Microsoft Sysmon 事件说明为例，事件 6、7、8、10、11 分别涉及驱动加载、模块加载、远程线程、进程访问和文件创建；其中模块加载事件需要配置，远程线程事件也不覆盖同进程执行或所有注入方式。具体产品是否采集这些事件，以及采集粒度，取决于配置与实现。

内存区域与执行地址​

可以关注可执行内存的类型、权限、来源和实际执行情况。例如 MEM_PRIVATE 的可执行区域、线程起始地址或当前执行地址不属于已知模块，都是值得继续追踪的线索。Windows 的 VirtualQueryEx 文档说明了 MEM_PRIVATE、MEM_IMAGE 和页面权限等属性。

但私有可执行内存不等于恶意：JIT、浏览器、游戏引擎和某些插件框架也可能产生它。还应核对进程角色、区域内容、调用栈、页面变化与后续行为；内存中没有 MZ 也不能排除 shellcode 执行或被处理过的 PE 映像。

采集链路的健康状态​

具备相应权限和能力的产品还可能结合内核事件、ETW Threat Intelligence、内存检查及云端关联分析，但不能假设某一种遥测会完整记录所有内存分配和权限变化。若怀疑 BYOVD 或其他致盲行为，应比对驱动加载、安全服务状态、本地事件、中心端心跳与上报量，确认是攻击行为未被检测，还是采集或上报已经受损。

PPL（Protected Process Light）能限制普通进程对受保护安全服务的访问和终止；它不是对内核权限滥用的绝对保证。可参见微软的反恶意软件服务保护说明。

研判顺序​

  1. 确认输入。 查清最终载荷来自文件、资源还是网络；磁盘上是否只有编码容器，是否另有侧载 DLL 或驱动。
  2. 确认进程关系。 区分同进程加载与跨进程注入；记录发起进程、目标进程和实际执行地址。
  3. 确认内存执行。 关联可执行区域的类型、权限、内容和线程 / 回调落点，避免只凭一次分配或一次文件读取下结论。
  4. 确认采集完整性。 对照文件、模块、内存、线程和安全产品健康事件，解释缺失的遥测，而不是将“没看到”直接写成“没有发生”。
  5. 再做家族归因。 将加载方式与配置、持久化、通信和样本证据结合；仅有内存执行或 ValleyRAT 名称不足以归因银狐。Check Point 后续研究也提醒，ValleyRAT 的公开构建器会削弱仅凭家族名称进行归因的可靠性。

小结​

内存执行会减少最终载荷的落盘和正常模块加载痕迹，但初始文件、私有可执行内存、执行流与后续行为仍可提供证据。分析时把加载方式、执行进程、EDR 采集状态分开核实，才能解释某条告警为什么缺失，以及剩余证据能支持多强的结论。
